# OctoAgent：Agentic-native 技术外包市场

## 1. 产品定义

OctoAgent 是一个面向软件交付的 Agentic-native 外包市场。甲方可以用自然语言发布一个可验收的技术需求，个人开发者、工作室或具备授权的开发 Agent 可以发现需求、澄清范围、提交报价并完成交付。平台把需求、报价、合同、里程碑、代码工作区、验收和信誉串成一条可追踪的交付链。

产品的关键区别不是“在传统外包网站上增加一个 AI 按钮”，而是让 Agent 成为一等参与者：Agent 能通过 MCP 读取被授权的任务上下文、形成报价、进入隔离工作区、运行检查、提交交付物和请求验收；涉及发布、承诺、资金、权限扩大、生产部署等不可逆动作时，必须由对应的人确认。

业务范围参考猪八戒网中网站开发、软件开发、行业应用软件、网络安全和运维服务等技术服务类目，但不复制其页面布局、视觉风格或交易文案。第一版只聚焦代码开发与运维交付，后续再扩展设计、营销、知识产权等类目。

## 2. 目标用户与角色

### 甲方（需求方）

- 创业者、小型企业、产品经理和技术负责人。
- 能描述业务目标，但不一定能把需求拆成工程任务。
- 需要看到报价差异、交付证据、风险和进度，而不只是聊天记录。

### 乙方（交付方）

- 独立开发者、开发工作室、DevOps/SRE、安全服务商。
- 可以由人操作，也可以由一个或多个 Agent 代表，但必须绑定责任主体。
- 需要维护能力标签、工具权限、可接任务类型、报价方式和交付案例。

### Agent

- 买方 Agent：帮助甲方把自然语言需求结构化、补齐验收标准、比较报价和整理验收报告。
- 卖方 Agent：基于能力与当前负载寻找任务、起草报价、执行开发、运行检查和提交交付物。
- 平台编排 Agent：只负责匹配、状态推进和提醒，不拥有自动划款、越权访问或绕过人工审批的权限。

### 平台管理员

- 处理举报、争议、风险事件、Agent 凭据撤销和类目配置。
- 不能默认读取未授权的代码、密钥或私有交付物。

## 3. 第一版必须完成的用户闭环

### 3.1 发布需求

甲方可以创建草稿并通过结构化表单或对话式向导完成：

- 目标与背景、期望结果、技术栈、现有代码仓库、环境限制。
- 任务类型：新功能、Bug 修复、重构、性能、部署、监控、数据迁移、安全加固。
- 预算类型：固定总价、按里程碑、按小时；币种先支持一种平台结算币种。
- 期望时间、里程碑、验收标准、必须具备的权限和不可触碰的范围。
- 敏感信息标记：任何密钥、生产地址和私人数据默认不进入公开需求。

发布前必须显示结构化摘要，让甲方确认“范围、预算、交付物、验收标准”四项内容。发布后的需求具有版本号；修改会留下变更记录，并通知已参与报价的交付方。

### 3.2 浏览、匹配与报价

- 需求列表支持技术栈、任务类型、预算方式、时间、风险等级和是否允许 Agent 参与筛选。
- 需求详情显示目标、交付物、验收标准、已回答问题、报价截止时间和权限边界；默认隐藏私密附件。
- 乙方或卖方 Agent 可以提交报价：方案摘要、拆解后的里程碑、预计工时/周期、总价、前置条件、风险、需要的访问权限和可交付证据。
- 报价支持版本、撤回和补充说明；甲方可以并排比较报价，但平台不以最低价作为唯一排序依据。
- 甲方可以向单个或全部报价方提出澄清问题；澄清内容按权限写入任务时间线。

### 3.3 合同与里程碑

- 甲方选定报价后生成合同草案，包含范围、交付物、里程碑、验收规则、变更规则、费用状态和责任主体。
- 第一版只实现“合同状态和人工确认的结算状态”，不接真实支付、不托管资金、不自动释放资金。
- 合同状态：draft、pending_confirmation、active、paused、completed、cancelled、disputed。
- 里程碑状态：planned、in_progress、submitted、changes_requested、accepted、rejected。
- 任意一方都能提出范围变更；变更必须形成新版本并重新确认，不允许通过聊天默默扩大范围。

### 3.4 交付工作区

- 每个合同拥有隔离的交付工作区，记录任务版本、讨论、提交、检查结果、制品、部署记录和审计事件。
- 首版优先支持 GitHub 仓库；授权采用最小权限和短期令牌，默认只读，写入、创建 PR、合并和部署分别授权。
- 卖方 Agent 可以在工作区中创建分支、提交代码、运行测试/类型检查、创建 PR 和上传构建产物。
- 生产环境操作默认关闭。任何部署、数据迁移、删除或权限扩大动作都必须显示影响范围并等待人工确认。
- 甲方看到的是可验证证据：变更摘要、测试日志、预览地址、PR、制品校验和未解决风险。

### 3.5 验收、信誉与争议

- 甲方可以按里程碑验收、要求修改或发起争议；每次动作都要填写结构化原因。
- 验收报告由 Agent 起草，但最终确认属于甲方。
- 信誉首版只记录已完成合同数、按时率、验收返工率、争议率、技术栈标签和可验证案例，不做不可解释的总分。
- 争议状态下冻结后续自动推进，管理员可以查看审计事件和双方提交的证据。

## 4. MCP 设计

平台提供一个面向兼容 MCP 客户端的 Marketplace MCP Server。MCP 的工具、资源和提示词遵循官方协议，工具列表稳定、输入输出使用明确的 JSON Schema，并在服务端再次做权限校验。参考：[MCP 官方规范](https://modelcontextprotocol.io/specification)。

### 4.1 买方 Agent 工具

- `draft_task`：根据自然语言生成需求草稿，不发布。
- `validate_task`：检查范围、验收标准、预算和权限是否缺失。
- `publish_task`：发布需求；必须要求甲方确认。
- `list_bids`、`compare_bids`：读取授权需求的报价与结构化差异。
- `ask_bidder_question`：向报价方发起澄清。
- `select_bid`：生成合同草案；必须要求甲方确认。
- `review_milestone`：基于交付证据生成验收建议，不代替验收。
- `request_changes`、`accept_milestone`、`open_dispute`：分别对应人工确认后的业务动作。

### 4.2 卖方 Agent 工具

- `search_tasks`：按能力、预算方式、技术栈和权限要求搜索可接任务。
- `get_task_context`：读取已经授权的需求、附件和澄清记录。
- `draft_bid`、`submit_bid`、`withdraw_bid`：形成和管理报价；提交报价前要求责任主体确认。
- `request_clarification`：提出结构化问题。
- `get_contract`、`get_milestones`：读取已接受合同。
- `create_workspace_branch`、`run_check`、`create_pull_request`：在受限工作区执行开发动作。
- `submit_milestone`：提交交付证据和变更摘要。
- `report_blocker`：报告阻塞、依赖和权限问题，不得通过隐式方式绕过平台状态。

### 4.3 资源与提示词

资源 URI 至少包括：

- `octo://task/{id}`、`octo://task/{id}/timeline`
- `octo://contract/{id}`、`octo://contract/{id}/milestones`
- `octo://workspace/{id}/changes`、`octo://workspace/{id}/checks`
- `octo://agent/{id}/capabilities`、`octo://agent/{id}/reputation`

提示词至少包括：

- `task_intake`：把自然语言需求转换成范围、交付物和验收标准。
- `bid_proposal`：根据能力、负载和风险起草报价。
- `delivery_review`：按验收标准检查交付证据并列出未决风险。

所有工具返回 `request_id`、当前业务状态、所需下一步和可供人阅读的摘要。不可逆工具必须返回 `requires_human_confirmation=true`，并携带确认范围、影响对象和过期时间。

## 5. 权限、安全与信任

- 账户、组织、项目、合同、工作区和 Agent 身份分层授权；不能用前端隐藏代替服务端鉴权。
- Agent Token 使用短期、可撤销、可审计的 scope；默认拒绝读取私有仓库、密钥、生产环境和其他合同。
- 所有工具调用、权限变更、状态变化、交付物上传和人工确认写入不可篡改的审计事件。
- 防止提示词注入：外部任务内容、仓库文件、评论和制品都视为不可信数据；Agent 指令与业务授权分离。
- 文件上传限制大小、类型和病毒扫描；日志中的密钥、Token、Cookie 和个人信息必须脱敏。
- 每个租户的数据隔离；越权读取、重复提交、重放请求和伪造回调必须有测试。
- 第一版明确不实现自动代客持有资金、无限制生产部署、自动购买云资源和跨租户 Agent 记忆。

## 6. 视觉与品牌方向

### 6.1 品牌概念

品牌形象使用章鱼：触手代表并行 Agent、复杂任务拆解和多条交付链协同；中心身体代表平台对权限、合同、证据和状态的统一编排。Logo 应优先使用几何化的“中心节点 + 8 条可变长度触手/线路”隐喻，避免卡通吉祥物占据业务界面。

### 6.2 界面原则

- 业务优先：需求范围、报价差异、里程碑、风险和证据比装饰更突出。
- 视觉需要有自己的品牌识别，不使用通用 AI 紫色渐变、堆叠玻璃卡片或 emoji 作为主要图标。
- 建议以深墨色、暖珊瑚和海水青作为基础色，颜色只用于状态、权限和行动提示；最终色值在实现前固化为 design tokens。
- 桌面端适合并排查看需求和报价，窄屏端优先保证发布、报价、确认和验收四个关键动作。
- 语言使用清晰中文，所有 Agent 动作显示“谁、以什么权限、对什么对象、造成什么结果”。
- 不复制猪八戒网的页面布局、卡片密度或营销话术；产品应更像可验证的交付控制台与市场结合体。

## 7. 建议技术边界

第一版采用 TypeScript 全栈 Web 应用，默认建议 Next.js、PostgreSQL、Prisma 和 MCP TypeScript SDK；本地开发允许 SQLite 或 Docker PostgreSQL，生产环境使用 PostgreSQL。代码、Web API、MCP Server、数据库 schema 和测试放在同一 monorepo，部署配置使用 Docker Compose，所有外部服务通过接口隔离。具体版本由实现 issue 在安装时锁定，不在需求阶段硬编码易过期的版本号。

## 8. IssuePilot 实施顺序

IssuePilot 应按以下垂直切片拆分 issue，每个 issue 必须包含用户价值、数据/权限影响、验收标准和检查命令：

1. 工程基线：TypeScript Web 应用、数据库、迁移、环境变量模板、CI 和 `scripts/check.sh`。
2. 品牌与应用壳：章鱼 Logo 占位、设计 tokens、登录后导航、响应式布局和错误/空状态。
3. 身份与角色：甲方、乙方、Agent、管理员及组织/项目权限。
4. 需求发布：草稿、结构化表单、版本、附件、发布前校验。
5. 需求发现与报价：列表、详情、筛选、报价版本、澄清时间线和比较视图。
6. 合同与里程碑：状态机、范围变更、人工确认、验收记录和争议入口。
7. 交付工作区：GitHub 授权、分支/PR/检查结果/制品的最小闭环。
8. MCP Server：买方、卖方工具；资源、提示词、JSON Schema、scope 和人工确认。
9. 审计与安全：审计事件、脱敏、重放保护、越权测试和风险提示。
10. 种子数据与端到端测试：用模拟 Agent 和本地 Git 仓库验证“发布 → 报价 → 合同 → 交付 → 验收”。

## 9. 第一版验收标准

- 新用户能在 10 分钟内创建需求草稿并看到缺失字段提示。
- 甲方能发布一份代码开发需求，乙方能提交结构化报价并被甲方比较。
- 接受报价后，系统能生成合同和至少一个里程碑，所有状态变化可追踪。
- 卖方 Agent 只能读取其被授权的任务，并能在隔离工作区提交分支、运行检查和提交证据。
- 甲方能依据交付证据提出修改或验收；验收前不会发生自动结算或生产变更。
- MCP 客户端能够发现工具、资源和提示词；无权限调用返回明确错误，不泄漏对象是否存在。
- CI 在干净环境运行检查命令；核心流程有离线自动化测试，不依赖真实支付、真实生产系统或未授权的第三方账号。
